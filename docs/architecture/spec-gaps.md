# Spec gaps: where the spec meets code

The spec is right about *behavior*. The rows below are the places where a literal reading breaks once it runs against real MCP clients, SQLite and git. Each row says what we build instead.

Status key:

- **Refinement**: keeps the spec's behavior and only fixes how it is built. No human approval needed.
- **Deviation (adopted)**: changes a "Suggested default" or build-brief detail. It was adopted with this architecture and is listed here so the human can see it.
- **Approved**: a behavior change the human approved on 2026-09-26.
- **Deviation (needs approval)**: a behavior change requested in this session and built on the branch; the human approves it before merging.

| # | Spec says | What breaks in code | What we build | Status | ADR |
|---|---|---|---|---|---|
| 1 | `wait` long-polls and returns at least every 60 s | MCP TypeScript SDK clients time out requests at 60 s by default, so a 60 s wait races the timeout. An idle agent looping on `wait` also adds roughly 300 tokens per minute (~18k per idle hour) to its context. | `wait` is capped at 50 s by default and can go longer only if S0 shows the client resets its timeout on progress notifications. The "nothing new" reply is a few tokens. | Refinement | [0001](adr/0001-piggyback-delivery.md) |
| 2 | Human and critical messages "interrupt wait" | The hub reaches the model only when the model calls a tool. MCP notifications never reach the model, so an agent that is working (not waiting) would never see the human. | **Piggyback delivery**: rt-agent adds an inbox banner to every Round Table tool result and puts human/control items inline. A pending `wait` resolves immediately on human or critical items. | Refinement | [0001](adr/0001-piggyback-delivery.md) |
| 3 | Stale = no hub call for 3 min | A model running a 10-minute build makes no hub calls but is alive, so it would be marked stale and lose its locks. | Two signals: **connection liveness** (transport pings from the rt-agent process) drives stale and gone; **attention** (time since the last model or hook tool call) only makes the leader ping the agent. | Refinement | [0002](adr/0002-liveness-vs-attention.md) |
| 4 | `rejoin(agent_id)` is a model tool | After a restart or context reset the model doesn't remember its agent_id. The spec also wants the model never to handle identity. | **Identity slots**: `rt-agent --slot A` stores the identity per slot and rejoins automatically before the first tool call. `rejoin` stays only as a manual retry. | Refinement | [0003](adr/0003-identity-slots-and-auto-rejoin.md) |
| 5 | Two live sessions with one key → pause both and alert | When a stdio MCP server restarts, the old and new processes normally overlap for a moment, so the rule would fire on every restart. | **Epoch fencing**: the newest proven session wins and older epochs get `fenced`. The pause-and-alert fires only on ping-pong (a fenced key coming back more than 3 times in 2 min). | Refinement | [0004](adr/0004-session-epoch-fencing.md) |
| 6 | "One command queue per project in the hub" | Repo locks and the global budget span projects, so per-project queues would need cross-queue locking. SQLite is single-writer anyway. | **One serialized command bus** for the whole hub. Isolation is logical: project_id scoping, one transaction per command, and a failing command flags only its own project. The log has `system`, `project:<id>` and `repo:<id>` streams. | Deviation (adopted) | [0005](adr/0005-single-serialized-writer.md) |
| 7 | Replay rebuilds the board; raw logs are kept 90 days | Once events are pruned you can't replay from zero, so time travel and rebuilds break after 90 days. | Events are **durable** (board versions, task states, decisions, votes, human and audit actions: never pruned) or **ephemeral** (chat, activity, log_action: pruned). Snapshots are written periodically and always before pruning. | Refinement | [0006](adr/0006-durable-and-ephemeral-events.md) |
| 8 | 20 sections, each with its own schema and API | Twenty projection tables and routers make a lot of code that drifts apart. Some "sections" are state machines (tasks, locks), not documents. | Two kinds: **document sections** (a generic versioned entry plus a per-section zod schema) and **state sections** (hub aggregates). One **section registry** drives routing, access control, notify rules and app tabs. | Refinement | [0007](adr/0007-two-section-kinds-and-registry.md) |
| 9 | "Opens a PR", "merged PR" | The MVP is local with a sample repo, so there is no PR object. An approval given at an older commit would still count after new pushes. | A `GitHost` port with **LocalGitHost**: a ChangeRequest is branch + base + head sha, tracked by the hub. Approvals and test results are tied to a head sha, and **the hub merges** when the done rule holds at the current head. GitHub comes later behind the same port. | **Approved** | [0008](adr/0008-local-git-host-and-change-requests.md) |
| 10 | Done = reviewer approval + a passing test_result | A test result posted by an agent is only a claim. "Tests pass on branch, fail on main" is only caught after the merge. | The hub runs `rules.test_command` itself on the **merge result** of main + head sha in a scratch worktree, then moves main by compare-and-swap. The tester agent's result is still required. | **Approved** | [0009](adr/0009-hub-runs-tests.md) |
| 11 | Timers everywhere (codes, grace, votes, stale, locks, budgets) | `setTimeout` is non-deterministic, can't be tested with a fake clock and is lost on restart. | A **Scheduler**: timers are events and fire as commands. The clock and id generator are injected into `core`. | Refinement | [0010](adr/0010-scheduler-and-injected-clock.md) |
| 12 | Leader-only tools | The MCP tool list is fixed when the server starts, but the role is known only after pairing. | rt-agent sends `tools/list_changed` once the role is known (S0 checks client support). The hub enforces the ACL on every call regardless. | Refinement | [0011](adr/0011-procedure-catalog-over-rest.md) |
| 13 | Human role only in the app; localhost only | Agents have a shell. They can `curl` a localhost REST API, and as the same OS user they can read the hub database and key files. | A separate `/app` endpoint with a one-time login URL, an HttpOnly cookie, and Host/Origin checks. Agent principals can't reach human procedures. The threat model says plainly that a malicious same-user agent is out of scope, and recommends a separate OS user for the hub. | Refinement | [0012](adr/0012-security-boundary-and-threat-model.md) |
| 14 | "Every agent stops at its next tool call" on pause | The hub only sees Round Table tool calls; Bash and Edit are invisible to it. | The **Claude Code hook adapter** (`rt hook pre-tool-use`, via the slot's rt-agent socket) denies tools while paused and logs every call. Without it, a pause lands at the next Round Table call. | Refinement | [0012](adr/0012-security-boundary-and-threat-model.md) |
| 15 | Token budgets per agent and task | The hub can't see token usage. | Time, attempts, files changed and review rounds are measured by the hub. Tokens and cost are self-reported (from `activity` or the hook adapter) and labeled best effort. | Refinement | — |
| 16 | Private keys in the OS keychain, falling back to a 0600 file | Node has no keychain API without native modules (keytar is deprecated), which also complicates Electron later. | A `KeyStore` port. The MVP ships the **0600 file store**; a keychain backend follows. | Deviation (adopted) | [0012](adr/0012-security-boundary-and-threat-model.md) |
| 17 | "The human dashboard uses the same API over REST" | Two APIs (REST for the app, WS for agents) for the same operations drift apart and need separate access checks. | One **procedure catalog** (zod input/output + allowed principals) served over the Transport to both rt-agent and the app. HTTP is kept for static files, `/login` and exports. | Deviation (adopted) | [0011](adr/0011-procedure-catalog-over-rest.md) |
| 18 | Milestones M0 → M7 as horizontal layers | Nothing touches a real MCP client until M4, so the riskiest assumptions (rows 1–5, 12, 14) surface late and force rework. | **Vertical slices, spikes first** (S0–S7). The scope is unchanged. | **Approved** | [0013](adr/0013-vertical-slices.md) |
| 19 | "Any agent" writes `incidents` | This contradicts "only hub and leader write the board". | The agent proposes, and a hub rule commits immediately with the agent recorded as author and `via: hub`. | Refinement | [0007](adr/0007-two-section-kinds-and-registry.md) |
| 20 | Opening a PR and posting test results have no dedicated tool | The model needs a clear, schema-checked way to do both. | `board_propose('artifacts', 'open', {kind: 'change_request', …})` opens a CR. Review and test outcomes go through `respond(request_id, result)` with a required `headSha`. No new tools. | Refinement | [0008](adr/0008-local-git-host-and-change-requests.md) |
| 21 | Package names `mcp-client/`, `human-app/` | "MCP client" is misleading: the package is an MCP *server* and a hub client. Also, the domain logic needs a home without IO. | Packages are `protocol`, `core` (new, pure), `hub`, `agent` (`rt-agent`), `cli` (new), `app`, `testkit`. | Deviation (adopted) | — |
| 22 | "Bring your own: any MCP client joins the hub" | Timeouts, `tools/list_changed`, server instructions and config files differ per client; S0 verified them only for Claude Code. | **Client profiles** in rt-agent: `rt agent install --client` writes each client's project config. Unverified clients get the safe defaults: `wait` under 50 s, static tool lists with hub-enforced roles, and a briefing in the first tool result. | Refinement | [0014](adr/0014-any-mcp-client.md) |
| 23 | D3: agents loop on `wait` until dismissed | Models treat the chat as the conversation: after pairing, or when only told to wait, they end their turn, and an MCP server can't wake them. Without a role prompt they don't know what to do. | The hub computes each agent's **next step from the board**, and rt-agent appends it to every tool result, with "waiting happens inside wait". Pairing hands control to the Round Table. The app flags idle agents so the human can type "continue". | Refinement | [0015](adr/0015-round-table-drives-the-loop.md) |
| 24 | Rejoin: "needs no human and no code: the agent proves it holds the private key" | In an IDE, every chat shares one rt-agent and its key store, so holding the key doesn't show which chat is calling. Rejoin by name let any chat become any paired agent. | Named mode: each approved chat gets a **chat token** (hash on disk) required on every call. A new chat that claims a paired name sends a **resume request** that the human must allow (phrase + code), and then the old chat is stopped. Fixed slots rejoin as in the spec. | Deviation (needs approval) | [0017](adr/0017-a-name-is-not-a-password.md) |
| 25 | "Bring your own: any MCP client joins the hub"; agents join by pairing from their own session | A chat client owns the loop: the hub can't wake a model, clients differ in timeouts and approval prompts, and a chat has no identity. | **Round Table runs the agents**: providers (CLI tools with credentials) configured in the app, agents started headless by the hub in their own worktrees, woken by a supervisor. Joining from a chat stays as a fallback. | **Approved** | [0018](adr/0018-round-table-runs-the-agents.md) |
| 26 | "Planning and approval: one human approval" before execution | The human may not be around at all (full auto), and a plan waiting for a click stalls the team. | A setting, `autonomy.planApproval`: `human` (the default, as the spec says) or `leader`, where the leader's commit is the approval and the human gets the plan as an FYI. | Deviation (needs approval) | [0020](adr/0020-settings-and-autonomy.md) |
| 27 | F2: "each agent proposes tasks"; the leader merges them | Measured on a real run: three agents proposed overlapping plans, the leader rejected the duplicates one by one, and each rejection woke its proposer for a turn. | With a leader, **the leader plans**: it proposes every task and commits the plan in one `board_commit {ticketIds}`; tasks may depend on each other by ticket id. Workers wait for the plan. Without a leader, workers propose as before. | Deviation (needs approval) | [0019](adr/0019-daily-driver-slice.md) |
| 28 | `send(to: all)`; `normal` is channel traffic | A hub-run agent turns every delivered message into a full CLI turn, so one status update to everyone cost a turn (and its tokens) per agent. | Only `human`, `critical` and `direct` messages wake an idle hub-run agent; `normal` and `digest` ones ride along with its next turn. A worker's message to everyone is `normal` at most, or refused when `messaging.workerBroadcast` is `off`. | Refinement | [0019](adr/0019-daily-driver-slice.md) |
| 29 | `rules`: "working rules … Human; team vote for additions", per project | People want rules that hold in every project, and rules only for the leader. | Hub-wide team and leader rules in Settings, plus each project's rules (`rules.text`, `rules.leaderText`). Hub-run agents get them in their kickoff and hear about changes with their next turn. | Deviation (needs approval) | [0020](adr/0020-settings-and-autonomy.md) |
| 30 | Human actions are "app only, never MCP"; no shell for the human | People debugging a team want to look around the repository and worktrees and run commands, without leaving the app. | A read-only Code tab (branches, history, worktrees, files, diffs) and a **terminal**: a shell on the hub machine over its own WebSocket, human cookie and same origin only, off by setting. Nothing typed is logged. | Deviation (needs approval) | [0021](adr/0021-the-humans-terminal.md) |
| 31 | Budgets and "human away" defaults arrive in S4; Settings, Metrics and notifications in S5; commits in logs in S6 | The first real project showed these are what makes the app usable day to day. | Pulled into **S2c**: project budgets (warn at 80%, stop at 100%), settings with per-project overrides, per-role model and effort, insights ("where the time went"), read-only git. | Deviation (needs approval) | [0019](adr/0019-daily-driver-slice.md) |

## S0 results

All five questions were checked on 2026-09-26 against Claude Code 2.1.283 and Node 24.21. Details are in [`spikes/s0-mcp/FINDINGS.md`](../../spikes/s0-mcp/FINDINGS.md).

- **Tool call timeout**: 60 s, and progress notifications do **not** extend it. `MCP_TOOL_TIMEOUT` in settings `env` **does**. `rt agent install` sets it to 300 s and runs `wait` up to 240 s; without install, `wait` is capped at 50 s (rows 1, 2).
- **`tools/list_changed`**: works mid-session (row 12).
- **Hook deny via unix socket**: works, with 5–13 ms latency (row 14).
- **node:sqlite**: WAL and FTS5 work, at about 3,700 transactions/s with full fsync (rows 6, 7).
- **Type stripping through workspace links**: works.
- **New finding**: without context, the model treats text appended by the server (banner, hook reasons) as a possible prompt injection and ignores it. With server `instructions` that define a factual `[Round Table]` status line, it acts on it. Recorded in ADR-0001 and ADR-0012.
